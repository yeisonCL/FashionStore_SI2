1. PERFIL
1.1 Introducción
En la actualidad, el sector del comercio minorista de moda ha experimentado una transformación acelerada hacia los canales digitales. Sin embargo, a pesar de la comodidad que ofrece el comercio electrónico tradicional, los consumidores se enfrentan a un desafío persistente al momento de comprar ropa en línea: la imposibilidad de probarse las prendas antes de adquirirlas. Esta incertidumbre sobre el entalle, cómo lucirá la ropa en su tipo de cuerpo o si el color será el adecuado, genera desconfianza en el cliente y resulta en altas tasas de devolución para las empresas, lo que impacta negativamente en la rentabilidad y la logística.
Por otro lado, las tiendas de ropa con presencia física enfrentan sus propios retos operativos, principalmente la falta de una integración eficiente de su inventario entre múltiples sucursales y sus plataformas de venta digital. Con frecuencia, los clientes acuden a una tienda buscando una prenda, talla o color específico, solo para descubrir que no está disponible en esa ubicación, lo que se traduce en una mala experiencia de usuario y en la pérdida de ventas potenciales por no contar con un sistema centralizado que gestione reservas y disponibilidad en tiempo real.
Para dar solución a estas problemáticas, el presente proyecto plantea el desarrollo de 
"
FashionStore
"
, una Plataforma Inteligente de Comercio Electrónico orientada a cadenas de tiendas de ropa. Esta solución tiene como propósito revolucionar la experiencia de compra al crear un puente perfecto entre el mundo físico y el digital, dotando tanto a los clientes como a los administradores de herramientas tecnológicas de vanguardia.
El valor agregado y el núcleo innovador de 
FashionStore
 radican en la integración de dos tecnologías clave: la Realidad Aumentada (AR) y la Inteligencia Artificial (IA). A través de la aplicación móvil, los usuarios tendrán acceso a un "vestidor virtual" mediante AR, permitiéndoles simular de manera interactiva cómo les quedarían las prendas utilizando la cámara de su dispositivo. Asimismo, la plataforma integrará servicios de Inteligencia Artificial que actuarán como un asesor de moda personalizado, sugiriendo prendas, colecciones y accesorios basándose en las preferencias del usuario, su historial de compras, sus tallas y las temporadas actuales.
Complementando estas innovaciones, el sistema administrará de manera integral el catálogo de prendas y el inventario distribuido en diversas sucursales. Los usuarios podrán realizar compras directas mediante pasarelas de pago digitales o, de forma alternativa, reservar prendas específicas desde la plataforma web o móvil para luego acudir a una sucursal física, probarse la ropa y concretar el pago en el punto de caja.
El desarrollo de esta plataforma se guiará bajo el rigor de la metodología del Proceso Unificado de Desarrollo de Software (PUDS) y el lenguaje de modelado UML 2.5. Para su implementación, se utilizará una arquitectura moderna que incluye Python y 
FastAPI
 para el desarrollo de un 
Backend
 robusto, bases de datos relacionales con PostgreSQL, Angular para el portal web administrativo y de ventas, y 
Flutter
 con Dart para la creación de la aplicación móvil multiplataforma que soportará las capacidades de Realidad Aumentada.

1.
4 
Descripción del Problema
Para comprender la magnitud de las deficiencias operativas en el sector 
retail
 de moda y, específicamente, en las cadenas de tiendas de ropa, es fundamental analizar el modelo de negocio actual y el flujo de trabajo fragmentado que emplean entre sus sucursales y sus canales digitales. El proceso de comercialización de prendas de vestir no es un evento aislado, sino una experiencia que inicia con la atracción visual, pasa por la verificación de entalle y culmina en la compra (física o digital). Actualmente, las cadenas de ropa operan con una profunda desconexión entre su inventario físico distribuido y sus plataformas de venta online, lo que genera serias limitaciones que afectan tanto al personal administrativo como a los consumidores. A continuación, se describe detalladamente cada uno de estos procesos y las problemáticas inherentes a su gestión actual.
Proceso 1: Búsqueda de Prendas y Experiencia de Prueba (Física y Digital)
El ciclo de compra comienza cuando el cliente busca una prenda específica, ya sea por temporada, talla o estilo. En el modelo digital tradicional (e-
commerce
 estándar o redes sociales), el principal problema es la total incertidumbre del cliente respecto al entalle: no existe forma de saber cómo le quedará la prenda, si el color le favorece o si la talla es la correcta para su tipo de cuerpo. Esta falta de visualización genera desconfianza, carritos de compra abandonados y, en caso de concretarse la venta, una altísima tasa de devoluciones. Por otro lado, en la búsqueda física, el cliente debe recorrer la tienda buscando su talla entre los percheros, muchas veces sin éxito, generando una experiencia de compra frustrante y dependiente de la asistencia manual de un vendedor.
Proceso 2: Gestión de Inventario Distribuido y Control de Stock
Al tratarse de una cadena de tiendas con múltiples sucursales, el manejo del inventario representa uno de los mayores cuellos de botella. Actualmente, cada sucursal maneja su stock de forma aislada o mediante sistemas de punto de venta que no se sincronizan en tiempo real con una base de datos central ni con la tienda web. Esto genera que un cliente vea un producto disponible en internet, pero al llegar a la sucursal física, la prenda ya haya sido vendida. Asimismo, si un vendedor de la "Sucursal A" no tiene una camisa en talla M, no tiene una herramienta rápida y 
confiable para saber si la "Sucursal B" la tiene en stock, perdiendo la oportunidad de retener la venta y derivar al cliente.
Proceso 3: Gestión de Reservas y Conexión 
Omnicanal
En el comportamiento de compra moderno, muchos clientes prefieren ver el catálogo desde su teléfono móvil y luego acudir a la tienda solo a probarse la ropa y pagar (modelo web-
to
-store). Sin embargo, el proceso actual carece de un sistema formal de reservas. Si un cliente pide por WhatsApp que le "guarden" una prenda, el proceso es completamente empírico, dependiendo de un papel con el nombre del cliente pegado a la ropa. Esto genera desorden en la sucursal, prendas bloqueadas que no se venden si el cliente no asiste, y conflictos cuando otro vendedor comercializa por error la prenda reservada, evidenciando una total falta de trazabilidad y omnicanalidad.
Proceso 4: Asesoramiento Personalizado y Recomendación de Moda
La asesoría de imagen y la recomendación de prendas complementarias (venta cruzada) es vital en el rubro de la moda. En la actualidad, este proceso depende exclusivamente de la memoria, el estado de ánimo o la experiencia del vendedor de turno en la tienda física. En el entorno digital, este asesoramiento es directamente inexistente. El cliente navega por un catálogo plano sin recibir sugerencias basadas en su historial de compras previo, sus tallas frecuentes, sus preferencias de color o la temporada actual. La empresa está perdiendo un valioso volumen de ventas al no aprovechar los datos del cliente para ofrecer recomendaciones inteligentes y personalizadas de outfits completos.
Proceso 5: Registro de Ventas, Cobros y Trazabilidad
Finalmente, el cierre de la transacción presenta una dualidad problemática. Las ventas realizadas físicamente se registran en un sistema de caja (POS) tradicional, mientras que las pocas ventas digitales se procesan por transferencias manuales o plataformas desconectadas. Esta falta de integración unificada impide calcular con precisión métricas vitales del negocio: cuáles son las prendas con mayor rotación, qué sucursal es más rentable, qué colores se venden menos en invierno, o cuál es el valor del ciclo de vida de un cliente recurrente. La información financiera y de comportamiento de usuario queda dispersa, dificultando la toma de decisiones estratégicas por parte de la gerencia.
1.4 Alcance
La 
Plataforma Inteligente de Comercio Electrónico para Tienda de Ropa (
FashionStore
)
 abarcará las áreas funcionales necesarias para gestionar de manera integrada una cadena de tiendas de ropa 
multiciudad
. El sistema centralizará el control de sucursales, inventarios distribuidos por tallas y colores, catálogo de prendas, reservas físicas (
web-
to
-store
), pasarelas de pago, vestidores virtuales con Realidad 
Aumentada (AR), recomendaciones impulsadas por Inteligencia Artificial (IA), puntos de venta en caja y reportes gerenciales.

). El flujo inicia cuando un cliente solicita un pedido; el sistema asigna la orden al repartidor más cercano, quien 
se dirige al establecimiento, retira la mercancía y realiza la entrega final validando la transacción mediante la app móvil.
b. Cálculo de pagos para una entrega:
El costo del servicio de entrega se determina mediante algoritmos que consideran múltiples factores:
Distancia geográfica:
 Kilómetros de recorrido entre la ubicación de origen (sucursal) y el destino final.
Peso y dimensiones:
 El tamaño y la fragilidad de la carga (por ejemplo, transportar una caja voluminosa de ropa versus un paquete ligero).
Frecuencia y demanda (Tarifa dinámica):
 Incremento de precios en horas pico, días festivos o condiciones climáticas adversas.
Tipo de servicio:
 Si se trata de un servicio exprés prioritario o un envío consolidado programado.
d) PUDS (Proceso Unificado de Desarrollo de Software)
El 
Proceso Unificado de Desarrollo de Software
 es un marco metodológico iterativo e incremental caracterizado por estar guiado por casos de uso, centrado en la arquitectura del software y enfocado en la mitigación continua de riesgos. Se divide en cuatro fases principales:
Inicio:
 Definición del alcance del proyecto, identificación de actores y viabilidad comercial.
Elaboración:
 Análisis detallado de los requerimientos, modelado de la arquitectura y diseño de los componentes clave.
Construcción:
 Desarrollo sistemático del código y construcción iterativa del producto de software.
Transición:
 Pruebas de integración, despliegue del sistema en entornos de producción y entrega final a los usuarios.

P1: Inadecuado registro de datos de postulantes e inscripción manual en ventanilla.

P2: Falta de un control sistematizado del estado de los requisitos físicos presentados.

P3: Inexistencia de un control automatizado para la planificación y capacidad de grupos.
Programar un algoritmo en el 
backend
 conectado a PostgreSQL que calcule automáticamente la cantidad de grupos necesarios según el número de inscritos, bloqueando las inscripciones con un tope estricto de 70 estudiantes por aula para evitar el hacinamiento.
P4: Deficiente control en la planificación y validación de requisitos de contratación docente.
Diseñar un submódulo de gestión docente que valide de forma estricta las restricciones del negocio: verificar perfiles profesionales (Diplomados, Maestrías), controlar que no existan cruces de horarios y restringir la carga horaria a un máximo de 4 grupos por docente.

2.1.1.8. Conclusión y Recomendación
En conclusión, la Facultad presenta problemas críticos en el proceso de admisión al Curso Preuniversitario debido al registro manual de postulantes, el seguimiento físico de requisitos documentales, la falta de integración con una pasarela de pagos y la ausencia de una planificación académica automatizada. Estas deficiencias ocasionan aglomeraciones en ventanilla, retrasos en la habilitación de postulantes, errores en la asignación de grupos, dificultades en el control de carga docente y vulnerabilidad en el registro de calificaciones.
Asimismo, la falta de un sistema centralizado limita la generación de reportes confiables y dificulta la toma de decisiones por parte de la administración académica. La gestión manual de notas, cupos por carrera y reubicación de postulantes en segunda opción aumenta el riesgo de errores en el proceso final de admisión.
Por tanto, se recomienda desarrollar una aplicación web que centralice la gestión del proceso CUP, permitiendo registrar postulantes, validar requisitos, procesar pagos en línea, calcular grupos según la capacidad máxima de 70 estudiantes, asignar docentes y horarios sin cruces, registrar calificaciones, determinar la admisión de los postulantes y generar reportes estadísticos en formato PDF. Esta solución permitirá mejorar la eficiencia del proceso, reducir errores humanos, optimizar la planificación académica y brindar información confiable para la toma de decisiones.

Registrar, revisar y validar los requisitos presentados por cada postulante.
Resumen

Actores
Personal de admisión, Administrador
Actor iniciador
Personal de admisión
Flujo del proceso
1. El actor ingresa al módulo de requisitos. 
2. Busca al postulante registrado. 
3. Visualiza los requisitos solicitados. 
4. Revisa la documentación presentada.
5. Marca cada requisito como cumplido, pendiente u observado. 
6. El sistema guarda la verificación. 
7. Si todos los requisitos están cumplidos, el sistema habilita al postulante para el pago.
Precondición
El postulante debe estar registrado en el sistema.
Postcondición
Los requisitos del postulante quedan registrados y actualizados.
Excepción
Postulante no encontrado, documentación incompleta o requisitos pendientes.

Registrar evaluaciones y notas
Propósito
Registrar las evaluaciones y calificaciones obtenidas por los postulantes en cada materia, ya sea de forma individual o mediante carga masiva desde un archivo Excel.
Resumen
Permite definir evaluaciones por materia, registrar las notas de los postulantes y realizar carga masiva de calificaciones mediante un archivo Excel, para calcular el rendimiento académico de los postulantes.
Actores
Docente, Administrador
Actor iniciador
Docente
Flujo del proceso

Excepción
Nota fuera de rango, postulante no pertenece al grupo, evaluación no registrada, docente no asignado, archivo Excel con formato inválido, columnas faltantes o datos inconsistentes.

Calcular admisión
Propósito
Determinar si el postulante fue admitido o no de acuerdo con sus notas, materias aprobadas y cupos por carrera.
Resumen
Permite calcular el resultado final del postulante, verificando aprobación por materia y asignación a carrera según cupos disponibles.
Actores
Administrador, Coordinador académico
Actor iniciador
Coordinador académico
Flujo del proceso
1. El usuario inicia sesión. 
2. Accede al módulo de admisión. 
3. Selecciona la gestión académica. 
4. El sistema consulta las notas del postulante por materia. 
5. Verifica que cada materia tenga nota mayor o igual a 60. 
6. Calcula el promedio final. 
7. Ordena a los postulantes aprobados según rendimiento. 
8. Verifica cupos disponibles en la primera opción de carrera. 
9. Si existe cupo, asigna la primera opción. 
10. Si no existe cupo, verifica la segunda opción. 
11. Registra el estado final de admisión.
Precondición
Todas las notas del postulante deben estar registradas y los cupos por carrera deben estar definidos.
Postcondición
El postulante queda registrado como admitido, no admitido o asignado a segunda opción.
Excepción
Notas incompletas, materia reprobada, cupos agotados o carrera no disponible.

Propósito
Verificar si existen cruces de horario entre docentes, grupos o aulas antes de confirmar una asignación.

Actor iniciador
Coordinador académico o Sistema

Procedimientos Almacenados
-- Registrar un nuevo postulante
CREATE PROCEDURE 
RegistrarPostulante(
IN nombre VARCHAR(100), IN ci VARCHAR(20))
BEGIN
   INSERT INTO 
postulante(
nombre, ci, fecha_registro) VALUES(nombre, ci, NOW());
END;
-- Registrar pago de postulante
CREATE PROCEDURE 
RegistrarPago(
IN id_postulante INT, IN monto DECIMAL)
BEGIN
   INSERT INTO 
pago(
postulante_id, monto, fecha) VALUES(id_postulante, monto, NOW());
END;
-- Validar requisitos de postulante
CREATE PROCEDURE 
ValidarRequisitos(
IN id_postulante INT)
BEGIN
   UPDATE postulante SET requisitos_completos = 1
   WHERE id = id_postulante AND documentos_entregados = 1;
END;
Triggers (Disparadores)
-- Actualizar cupo del grupo al insertar un postulante
CREATE TRIGGER ActualizarCupo AFTER INSERT ON postulante
FOR EACH ROW
BEGIN
   UPDATE grupo SET cupo_actual = cupo_actual + 1 WHERE id = NEW.id_grupo;
END;
-- Actualizar estado de pago
CREATE TRIGGER ActualizarEstadoPago AFTER INSERT ON pago
FOR EACH ROW
BEGIN
   UPDATE postulante SET pago_estado = 'Completo' WHERE id = NEW.id_postulante;
END;
-- Actualizar promedio de notas al modificar notas
CREATE TRIGGER ActualizarPromedio AFTER UPDATE ON nota
FOR EACH ROW
BEGIN
   UPDATE grupo SET promedio_grupo = (
      SELECT 
AVG(
puntaje_obtenido) FROM nota WHERE id_grupo = NEW.id_grupo
   ) WHERE id = NEW.id_grupo;
END;

7.1 Herramientas de desarrollo de la aplicación WEB
1. Herramientas de Diseño y Modelado
StarUML
 
Herramienta UML para representar gráficamente la estructura y procesos del sistema.
Ventajas: 
Facilita la creación de diagramas de clases, casos de uso, secuencia y otros. 
Desventajas: 
Puede ser innecesario si se usa metodología ágil con poca documentación.
 
Diagrams.net (Draw.io)
 
Aplicación online para crear diagramas de flujo, diagramas de procesos, y prototipos de interfaces.
Ventajas: Gratuito, 
flexible y colaborativo. Compatible con exportación a múltiples formatos
. 
Desventajas: 
Menos especializado en wireframes de UI comparado con Figma o Moqups.
 
2. Control de Versiones
Git + GitHub
 Gestión de código fuente y colaboración entre desarrolladores.
Ventajas
: 
Historial de cambios, revertir errores, uso de ramas para funcionalidades. 
Repositorios remotos, control de acceso, issues y pull requests. 
Permite implementar metodologías ágiles (Git Flow). 
Desventajas
: 
Curva de aprendizaje inicial. 
Requiere conexión a internet para sincronización. 
 
3. Entorno de Desarrollo
Laragon / XAMPP
 
Servidores locales con Apache, PHP y PostgreSQL para pruebas y desarrollo.
Ventajas: 
I
nstalación rápida y sencilla. 
Permite levantar rápidamente un entorno completo para pruebas locales. 
Laragon ofrece entorno portable y gestión de múltiples versiones de PHP. 
Desventajas: 
Conflictos de puertos si existen otros servicios corriendo. 
Configuración diferente según Windows o Linux; en Linux se recomienda LAMP nativo para producción.
Composer
 Gestor de dependencias para Laravel.
Ventajas
: Instalación y actualización de librerías PHP necesarias. 
Desventajas
: Requiere configuración del PATH en Windows. 
 
4. Tecnologías de Desarrollo Web
Frontend
HTML5, CSS3, JavaScript, 
React
 
Ventajas
: Interfaces modernas, interactivas y dinámicas. 
Desventajas
: Curva de aprendizaje si no se domina React. 
CSS Frameworks
Bootstrap / TailwindCSS para diseño responsivo. 
Backend
PHP (Laravel)

Ventajas

Desventajas
: Curva de aprendizaje si no hay experiencia previa.

DomPDF
 Generación de reportes, comprobantes y constancias en PDF desde plantillas HTML.
Ventajas
: Integración sencilla con Laravel. 
Desventajas

 Sistema relacional ampliamente compatible con Laravel.
Ventajas

Conclusión
El desarrollo del sistema de información para la 
gestión de admisión de estudiantes del proyecto CUP

La implementación de 
StarUML y diagrams.net

 y el 
frontend con React
.

Postulante
, 
Carrera
, 
Grupo
, 
Pago
, 
Nota
 y 
Asistencia
